GETTING STARTED

Your guidebook, connected.

Carrots is a static app. Upload these files directly to GitHub Pages; there is no build step.

1. Finish Firebase setup

  1. The separate Firebase project glauco-3985e and three member UIDs are configured in config.js.
  2. Enable Authentication → Sign-in method → Google. Add snowsences.github.io under Authentication → Settings → Authorized domains (hostname only, without the repository path). If using a custom domain, add that hostname too.
  3. Create a Cloud Firestore Standard edition database in production mode. Keep the default database ID.
  4. Paste the minimal rules below into Firestore → Rules and publish. These rules allow the three configured members. They are also included in firestore.rules.
  5. Reload Carrots while online and sign in with an authorized Google account.

The Firebase API key and UIDs are public identifiers. Firestore rules enforce access. Authorized members use the same shared collection. Firebase Storage is not used. Google sign-out clears local guides, photo overrides, and downloaded photos.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isCarrotsMember() {
      return request.auth != null
        && request.auth.uid in [
          '4ct4jQf9cPhbzqiasFT56Mav7Ds1',
          '12JhGJFUeJf4rf61K6bCTO0WBAQ2',
          'xND2OutlnVO2Wj81riAtoXdIdJc2'
        ];
    }
    match /glauco/shared/{document=**} {
      allow read, write: if isCarrotsMember();
    }
  }
}

2. Enable photo replacement

Photo replacement uses the Cloudflare Worker in cloudinary-worker.js so the Cloudinary API secret never enters the app. It supports attraction photos, a personal default photo for each wildlife species, and photos attached to wildlife notes. Uploaded images are public Cloudinary assets.

  1. Create a module Worker and paste in cloudinary-worker.js.
  2. Add the plain-text variables CLOUDINARY_CLOUD_NAME=myranker, FIREBASE_API_KEY=AIzaSyB5RnX8nf00fdvDCkpRNn39NiQp_ldbREE, ALLOWED_UIDS=4ct4jQf9cPhbzqiasFT56Mav7Ds1,12JhGJFUeJf4rf61K6bCTO0WBAQ2,xND2OutlnVO2Wj81riAtoXdIdJc2, and ALLOWED_ORIGIN=https://snowsences.github.io.
  3. Add CLOUDINARY_API_KEY and CLOUDINARY_API_SECRET as encrypted Worker secrets. Never put the API secret in config.js, GitHub, or browser code.
  4. Deploy the Worker at https://travel-guide.allenkevinc.workers.dev/. The app is already configured for this address.

3. Prepare an import file

Download the schema and attach it to ChatGPT with a Lambus export, a list of places and attractions, or the region and habitats for a local wildlife field guide. Existing guidebook files remain compatible without changes. Standalone wildlife field guides use version 6.

Download import schema

Use this prompt:

Create a Carrots guidebook file following the attached Carrots import-schema.json exactly.

Choose the format from my source material:
- For a Lambus export, create a dated trip using days. Use ONLY the Daily Plan. Include temples, historic sites, museums, galleries, natural attractions, and substantive cultural visitor experiences. Exclude restaurants, shops, transport, flights, hotel rests, and internal reminders. Assess mixed shopping/workshop entries before including them. Omit days with no qualifying attractions.
- For a written list of places and attractions, create a general destination guide with guideType "destination" and places. A place is a city, town, island, region, or other useful geographic grouping, such as Venice, Florence, or Rome. Keep attractions under the place supplied by the user. Add an optional neighborhood to an attraction when it is useful and reliably known. Do not add dates, days, visit times, itinerary assumptions, or comparisons. Each attraction must stand on its own.
- For a local or home-area field guide, create a standalone guide with guideType "wildlife". Include wildlife areas and species, but omit dates, days, places, attractions, comparisons and customs. Seen toggles, dated timeline notes and user photos are stored by the app and must never be written into the import file.

Choose visible main tabs with the optional guide-level tabs array. Values can be "trip", "customs" and "wildlife". Settings is always shown, and the app keeps the standard tab order. Omit tabs for the defaults: dated trips show all three, destination guides show Trip and Customs plus Wildlife when wildlife content exists, and standalone wildlife guides show only Wildlife. Examples: Venice and Rome can use ["trip","customs"], while a home wildlife guide can use ["wildlife"].

For a dated trip only, preserve full trip dates and infer the year only from the export's trip dates. Create a descriptive title for each day. Order days chronologically; order attractions by scheduled visit time when available, otherwise retain source order. Keep optional visitTime as a display string.
Write original, researched guide content: summary about 100–150 words in short paragraphs, plus about 300–600 additional words under helpful section headings. Scale detail to significance. Explain history, context, and specific things to notice on site. Use a few applicable key facts. Avoid invented stories or unverifiable claims. Distinguish tradition or disputed interpretations from established facts. Link to Wikipedia where an article exists and include supporting primary/authoritative sources. Record the research date. Practical information, if included, must be dated and verified.
Use 1–3 verified, suitably sized public Wikimedia photos per attraction, or [] when none is suitable. Use direct HTTPS image URLs from upload.wikimedia.org or thumb.wikimedia.org, with a small thumbnailUrl. Aim for 1200–1600px guide images and about 320px thumbnails. Verify the file's creator, source page, license and license URL. Do not invent image URLs or hotlink unrelated sites. coverUrl may use the first suitable attraction photo, or an empty string. For a dated trip, headerUrl may provide a separate public image for the fixed Trip Details header. Omit headerUrl to keep existing files compatible and use the cover image instead.
For dated trips only, make the sites build a narrative across the trip. For attractions after the first, look for meaningful comparisons to sites already visited, but apply a strict editorial test: does the connection teach the reader something specific and interesting? Put this material in comparisons: [{"attractionId":"earlier-site-id","paragraphs":["Original comparison text"]}]. Reference only attractions earlier in the itinerary, including earlier stops on the same day. Never preview, name, describe, or compare with future attractions in the guide text. Compare a concrete architectural feature, historical period, religious idea, carving style, or scale rather than repeating generic descriptions. Omit comparisons or use an empty array where no useful comparison is supported. Do not fill a quota or force links between unrelated places. Avoid generic similarities such as both having craftsmanship, atmosphere, or conservation needs. Never invent a connection. The app displays this content in the Comparisons tab with links to earlier sites. Destination guides must omit comparisons entirely.
Add notice to each attraction: exactly three short, specific things to notice, preferably one sentence fragment each, such as a carving, architectural feature, or viewpoint. These appear above the summary. Avoid vague instructions such as “enjoy the atmosphere.”
Add a short guide-level glossary array: [{"term":"term","definition":"Brief, researched definition"}]. Include recurring terms used in the guide. Explain each clearly and keep the glossary useful across the whole guidebook. It appears in Customs, and matching terms in guide prose open a definition when tapped. Add optional aliases for plurals or alternative spellings, for example {"term":"Naga","definition":"...","aliases":["nagas"]}. Use separate aliases for a combined glossary title. All terms and aliases must be unique. Define unusual terms briefly on first use too. Do not use em dashes. Prefer really or omit unnecessary emphasis.
Add researched local customs and language content at guide level as customs: {"guides":[{"id":"country-or-region","name":"Country or region","intro":"Brief context","sections":[{"heading":"Meals and tipping","paragraphs":["Original, verified guidance."]}],"language":"Italian","lang":"it","phraseNote":"Approximate pronunciation guidance.","phrases":[{"meaning":"Thank you","native":"Grazie","pronunciation":"GRAH-tsyeh"}],"sources":[{"title":"Official source","url":"https://example.org/replace-with-verified-source"}],"researchedAt":"YYYY-MM-DD"}]}. The example is structural; replace every placeholder with researched content and an actual research date. Use one entry per country, region or language as useful. Cover etiquette, restaurant tipping, practical transport apps, payments and useful local advice, avoiding generic filler. Verify practical claims and phrase spelling/pronunciation, distinguish advice from customs, and keep each guide independent of itinerary order. Each entry needs a unique ID, name, actual research date, and sections or useful phrases. Phrase entries are objects, not arrays. If phrases are supplied, include a language name and tag. There can be up to 12 customs guides, 15 sections and 40 phrases per guide; each guide is limited to 50 KiB and all customs content to 100 KiB. Imported customs replaces the full bundled country list for this guidebook, so include every country or region wanted. Omit customs or use {"guides":[]} to retain the built-in Cambodia, Thailand and Peru fallback. This optional section works for dated trips and destination guides, syncs, and is saved for offline reading. Do not add customs to each attraction.
Add optional history: [{"year":1186,"label":"1186 CE","title":"Monastery dedicated","text":"A concise, sourced explanation, naming a ruler or patron when relevant."}]. Sort events chronologically. The numeric year is a sorting anchor; the label must reflect the evidence's real precision, such as “Late 12th century”, without inventing an exact date. Focus on construction, a meaningful change of use, or a significant reconstruction. Do not add a timeline to a contemporary workshop or other attraction merely to fill space. In dated trips, the app draws the current site's milestones alongside the earliest milestone of earlier sites referenced in its comparisons. Destination guides show only the current attraction's history. Future itinerary attractions are never included.
Add optional originality: ["Concise, specific paragraph about what survives, what was altered historically, or what has been reconstructed."]. Explain something observable, such as replacement bricks, reassembled stonework, later religious alterations, or original imagery beneath modern finishes. Cite a reliable source. Do not guess the age of a surface from its appearance. Omit the field where there is nothing meaningful to say. Later historical changes can be significant too.
Use stable IDs containing only letters/numbers/hyphens/underscores, unique within their scope. If revising an earlier file, retain IDs. No HTML or Markdown in guide text; paragraphs are plain strings. Omit empty days or places. Maximum 400 attractions and 5 MB guide metadata per guidebook; maximum 12 MB per file.
Wildlife: include an optional wildlife object with areas and species. For regional browsing use browseByArea: true and give each species areaIds matching those areas. Each region groups entries as Plants, Birds and Other animals. Store only the common and scientific name, kind, group, regional membership, clear public identification photo(s), How to Recognise (identification), a short At a glance (summary), and an optional wikipediaUrl if a relevant article exists. Keep photo attribution and licence metadata in the file. Do not add Where to look, attraction links, extra species sections or other further reading. Use original, concise text and meaningful visual identification clues. Research taxonomy and regional occurrence during preparation, and do not treat observation counts as encounter probabilities. Follow the user's requested counts; for future guides agree a smaller selection rather than defaulting to hundreds. Add extra photos only for useful variation or plant parts. The app must work offline without live species API calls. When updating a guide, preserve its ID and all existing content.
Return a downloadable UTF-8 JSON file with format "glauco-trip-file", version 6, and trips. Do not insert it into app files or include private notes from unrelated source material.

In Carrots, open Settings and choose Import guidebook, select the prepared JSON file, and review its counts. For duplicates choose Import as new or Replace existing. Replacement preserves archive status and personal wildlife records. The JSON file is your source copy; Carrots does not export backups or edit guide content.

4. Take it offline

Open a trip or destination guide and choose Download. Keep Carrots open until it reports that the guide is ready. Downloads include the guide text, checklists, history timelines, originality notes, tappable glossary definitions, cover, dedicated header image, thumbnails, and full guide photos, including any Cloudinary replacements. Dated trips also include comparisons. Imported Customs content is included in each guide download. The built-in Customs guides remain cached with the app as a fallback. Settings shows the saved payload size and lets you update or remove each download. Size excludes browser database and cache overhead.

The first Google sign-in requires connectivity. Later you can reopen downloaded guides while offline using the saved authorized session. External Wikipedia and source links require internet access. No Google account credentials are stored by Carrots.

Photos must allow cross-origin downloads. A failed or interrupted download is never marked complete; an older successful download stays available during an update. For a blocked image, prepare a revised guidebook file with a supported Wikimedia URL. Images must be raster images, no larger than 8 MB each, with at most 300 MB of photos per guidebook.

Offline downloads belong to each browser or installed app. Browsers can remove stored data under storage pressure; Carrots requests persistent storage after downloading. Save your original import file and check that the guide is ready before travel.

Install on Android through the in-app Install prompt or Chrome’s Add to Home Screen. On iPhone, use Safari → Share → Add to Home Screen. The layout includes safe-area padding and bottom navigation.

Updates and synchronization

Imported content saves locally first and syncs when online. Imports upload a new immutable guide version, then switch the guidebook to it atomically. Archive and restore also sync. An archived guidebook can be deleted with confirmation in Settings while online. Deletion removes it from the collection and clears downloads as devices sync; a small deletion marker prevents pending older changes from restoring it. You can import the source JSON again. If the same guide changes on another device before a pending change syncs, Settings asks you to use the synced version; re-import the original file if needed.

Old guide versions remain in Firestore so interrupted imports and older devices can read safely. For three people this is small; old versions can be removed manually in the Firebase console after all devices have synced.

Before publishing future code releases, increment the same version in sw.js, release.json, app.js, the release meta and asset URLs in index.html, and manifest.webmanifest. The app checks while online and offers Update. It avoids reloading during a dialog, download, or unsynced change.

Changing config.js alone is fetched fresh on the next online reload. When changing image hosts, also update the CSP in index.html, the allowlist in sw.js, in the app. HTTPS only; public image URLs are required.

Place categories

Destination-guide entries may include category: attraction, dining or neighborhood. A Place containing several categories displays category tabs. Previous and next stay within the current category. Older files default to Attraction and need no changes.
